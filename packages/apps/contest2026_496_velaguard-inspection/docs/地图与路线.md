# 地图与路线

本文说明本工程地图数据的**来源、坐标系、四条固定路线的完整航点、区域分区块**，
以及**怎么把它换成你自己场地的真实航点**。所有数字都是从源码读出来的，不是估计值。

相关源文件：`src/common/map-data.js`（自动生成）、`src/common/map.js`、`src/common/data.js`、`tools/ros-map-to-vector.js`、`tools/gen-waypoints.js`。

### 生成命令

```powershell
node tools/ros-map-to-vector.js --auto
```

`--auto` 直接用上面归档好的那一份；也可以显式指定：

```powershell
node tools/ros-map-to-vector.js <classroom.pgm> <classroom.yaml> --out src/common/map-data.js
```

产出 **`src/common/map-data.js`（3.5 KB / 3,575 B）**，内容为：

| 导出 | 内容 |
|---|---|
| `MAP_META` | `name` / `source` / `gridW` / `gridH` / `resolution` / `origin` / `width` / `height` / `bounds` |
| `WALLS` | **55 个墙块**（矩形，米，地图坐标系），外墙与固定障碍 |
| `GAPS` | 7 处外边界缺口（门洞/通道中心点） |

### 转换算法（刻意朴素）

1. 读 PGM（P5 二进制）与 YAML 的 `resolution` / `origin`，把像素映射回米；
2. **行优先扫描**占据格（灰度值 ≤ 60 视为墙），用「行程 + 纵向合并」压成矩形；
3. **丢掉碎块**：面积 < 0.04 m²（约 4×4 格）的按建图噪点处理；
4. 顺带统计四周墙体上的**缺口**，打印出来供人工确认（见第五节）；
5. 按保留矩形的包围盒算出 `MAP.bounds`。

> ⚠️ `src/common/map-data.js` 是**生成物**，文件头写了「请勿手改」。
> 要换地图就重跑命令，要改航点就改 `data.js`（第六节）。

## 二、两个坐标系与换算

工程里同时存在两套坐标，混用是最容易出错的地方。**换算只在一个函数里做**。

| | 地图坐标系 | SVG 屏幕像素 |
|---|---|---|
| 单位 | 米 | px |
| 原点 | 左下（`origin [-4.61, -4.1, 0]`） | 左上 |
| x 轴 | 向右为正 | 向右为正 |
| y 轴 | **向上为正** | **向下为正**（翻转） |
| 用途 | `data.js` 里所有航点 / 墙块 / 区域块 | `renderMap()` 输出的 `<svg>` |
| 与车端关系 | **与车端 ROS 地图同一套** | 只在本机显示 |

### 换算唯一入口：`src/common/map.js` 的 `makeProjector`

```js
export function makeProjector(map, width, height)   // → project(x, y) → { sx, sy }
```

排版参数（`MAP_LAYOUT`，`src/common/map.js`）：

| 参数 | 值 |
|---|---|
| `SCREEN_W` × `SCREEN_H` | 720 × 1280（openvela goldfish 竖屏） |
| 画布高 `MAP_LAYOUT.height` | 460 |
| 左右留白 `padX` | 16 |
| 画布内边距 `inner` | 14 |
| 可用宽 `usableW` = 720 − 16×2 − 14×2 | 660 |
| 可用高 `usableH` = 460 − 14×2 | 432 |

**取景按 `MAP.bounds`（实际有墙的范围）而不是栅格名义尺寸**：

| | x | y | 跨度 |
|---|---|---|---|
| `MAP.bounds` | **−4.51 ~ 12.84** | **−3.85 ~ 5.70** | 17.35 m × 9.55 m |
| 名义尺寸 | −4.61 ~ 12.89 | −4.10 ~ 5.75 | 17.50 m × 9.85 m |

> 原因：车端真图四周有大片空白（未知区被裁掉了），**按名义尺寸取景会把四条路线挤成一小团**。

比例尺取两轴较小者：

```text
scale = min(660 / 17.35, 432 / 9.55) = min(38.04, 45.24) = 38.04 px/m
```

代入实际参数后，换算就是一个固定的仿射变换（y 轴翻转在 `offY` 里）：

```text
sx = 201.6 + x × 38.04
sy = 265.2 − y × 38.04
```

校验（脚本算出的实际值）：

| 输入（米） | 输出（px） |
|---|---|
| `(-4.51, 5.70)` 左上角 | `(30.0, 48.4)` |
| `(12.84, -3.85)` 右下角 | `(690.0, 411.6)` |
| `EN01 (-3.50, 3.60)` | `(68.4, 128.2)` |
| `EN03 (-2.60, 4.50)` | `(102.7, 94.0)` |

小车朝向也要翻：`yaw` 是地图坐标系弧度，SVG 里取负 —— `deg = -yaw × 180 / π`。

> 这条约定（y 轴翻转）是本节最容易错的一处，**单测里锁住了**。

## 五、怎么改成真实航点

### 步骤

1. **改 `src/common/data.js` 的 `WAYPOINTS`** —— 每个航点 `{ id, x, y, yaw, name }`，
   `x` / `y` 是**地图坐标系（米）**，与车端 ROS 地图同一套，**不是屏幕像素**；
2. **改同文件的 `ROUTES`** —— 每条路线是一串 `{ wp: '航点ID', dwell: 秒 }`；
3. **必须跑校验**：

   ```powershell
   node tools/gen-waypoints.js --check
   ```

   退出码 0 = 全部合规；非 0 = 有不合规项，并逐条打印原因。

### 校验的约束（`gen-waypoints.js --check` 实际检查的）

| 约束 | 阈值 | 来源 |
|---|---|---|
| 单步距离 | **≤ 1.0 m** | `LIMITS.step_distance_max_m`（与 `patrol_zones.json` 的 `step_distance_max_m` 对齐） |
| 单条路线总长 | **≤ 3.5 m** | 脚本内硬编码 |
| 航点位置 | 必须在**可行区域内**（`MAP.bounds`：x −4.51~12.84，y −3.85~5.70） | `MAP.bounds` |
| 航点数 | ≥ 2 | 脚本 |
| stop 引用 | 每个 `stops[].wp` 都必须能解析到真实航点 | `waypointById()` |

校验输出示例（当前状态）：

```text
  ok   route_entrance   4 点 / 2.30 m / 最长步 0.90 m
  ok   route_aisle      4 点 / 2.60 m / 最长步 0.90 m
  ok   route_exhibit    4 点 / 2.70 m / 最长步 0.90 m
  ok   route_equipment  4 点 / 2.70 m / 最长步 0.90 m

整条巡检路线总长：10.30 m（四条短路线首尾相接）
结论：全部合规
```

### 从一条折线自动生成航点

不想手填坐标时，用生成模式：把折线骨架写进 `tools/gen-waypoints.js` 的 `SKELETON`，
脚本按 **`STEP = 0.5 m`** 采样（沿折线插点、**强制以拐点收尾**，保证每段 ≤ 0.5 m 且每个明显拐弯处都有航点），
打印出可直接贴进 `data.js` 的 `WAYPOINTS` 表：

```powershell
node tools/gen-waypoints.js
```

> 为什么要有这个脚本：路线坐标**手算极易出错**。第一版按直觉写的 `route_aisle`
> 有一段实际长度是 **2.96 m**，而方案二自己写的约束是「单步远小于全局上限（1.0 m）」——
> 手算看不出来，脚本一眼就看出来。

### 设计约束（有意为之，别随手放宽）

1. **路线只由航点编号组成**，任务单里**不出现坐标 / 速度 / 时长**。
   车端拿到的只是「执行 `route_entrance`」，**无法被诱导跑任意轨迹**。
2. 坐标是**地图坐标系（米）**，与车端 ROS 地图同一套。屏幕换算只在 `map.js` 里做，
   **换屏、换任务都不用动 `data.js`**。
3. 每条路线都短：**2~3 段、总长 ≤ 3.5 m、每段 ≤ 1.0 m**。
   小车行为只用最朴素的原语：**直行 + 到点停留 + 转向下一段**。
4. `dwell` 对应车端 `dwell` 原语，**不发速度**。

相关阈值（`data.js` 的 `LIMITS`）：

| 键 | 值 | 含义 |
|---|---|---|
| `step_distance_max_m` | 1.0 | 单步距离上限 |
| `demo_speed_mps` | 0.8 | 演示推进速度（真车实测巡检速度是 0.12 m/s，演示放快否则一段要 20 秒） |
| `receipt_timeout_s` | 20 | 连续多少秒收不到回执判失联 → 阻塞 |
| `task_deadline_s` | 180 | 单任务时限，超时判阻塞 |
| `battery_min` | 20 | 电量低于此值不派长任务 |

## 六、外边界缺口（门洞）与「只画图」边界

### 缺口是怎么检测出来的

`tools/ros-map-to-vector.js` 的 `findGaps(occ, w, h, band = 3, minLen = 6)`：

1. 沿**四条外边界**各取一条 **3 格宽（= 0.15 m）**的边带；
2. 在边带内找**连续非墙**的行 / 列区间（上下边按列扫，左右边按行扫）；
3. 长度 **≥ 6 格（= 0.30 m）**的连续段才算一个缺口（滤掉建图毛刺）；
4. 栅格区间换算成米，输出**中心点 + 宽度**。

检出结果（当前 `classroom.pgm` 共 **7 处**，即 `map-data.js` 的 `GAPS`）：

| 边 | 中心 (x, y) | 宽度 |
|---|---|---|
| `top` | (−3.79, 5.75) | 1.65 m |
| `top` | (6.21, 5.75) | 13.35 m |
| `bottom` | (4.14, −4.10) | 17.50 m |
| `left` | (−4.61, 2.43) | 6.65 m |
| `left` | (−4.61, −3.40) | 1.40 m |
| `right` | (12.89, 5.03) | 1.45 m |
| `right` | (12.89, −1.35) | 5.50 m |

> 这些缺口是**打印出来供人工确认**的，同时也落在 `MAP.gaps` 里备查。
> `renderMap()` **不绘制** `gaps` —— 它只画 `walls`、`ZONE_BLOCKS` 和四条路线。

### 边界：这些轮廓**只用于画图，不参与任何控制逻辑**

这是本方案的一条硬边界，写在三个地方（`map-data.js` 文件头、`ros-map-to-vector.js` 文件头、`data.js` 的 `MAP` 注释）：

| 是 | 不是 |
|---|---|
| `WALLS` / `GAPS` 是**画图用的矢量近似** | 不是导航地图、不是代价地图、不是碰撞检测输入 |
| 路线是**预设的**，车端只沿线走 | 不做路径规划、不做避障、不做动态重规划 |
| 航点坐标与车端 ROS 地图**同一套坐标系**，可直接交接 | 本工程**不声称**具备 SLAM / 导航 / 避障能力 |

> 为什么要有这条边界：快应用这一侧只负责「显示」与「派单」，
> 一旦轮廓进入控制回路，就必须承担建图精度、坐标系标定、动态障碍物等一整套工程责任，
> 那是车端定位/导航栈的事，不是这个界面应用该做的事。**改动时请保持这条边界。**
