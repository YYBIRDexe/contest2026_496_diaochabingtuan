> 原因是当时设备上的语音管线正占用着麦克风，我抢不到设备而采到空数据。
> 下面是基于实测证据的最终结论。

（b）**麦克风拾音电平偏低**，现场人声识别不出来。

## 二、设备上已有一条现成的语音管线

这是最关键的发现。`/home/sunrise/voice_pipeline/` 里是一套完整、
久经调试的语音系统，且**一直在运行**：

```
PID 2779  voice_button.py --trigger fifo --fifo /tmp/voice_trigger \
              --agent-backend command \
              --agent-cmd python3 .../llm_intent.py \
              --cloud-first --vcmd-exec --tts --tts-prompt
PID 2900  wakeword.py --fifo /tmp/voice_trigger --lang en
```

### 用法（来自 `唤醒词说明.md`）

```
对着板子说「小陈同志」→ 它说「请讲」→ 再说指令 → 识别 → 下发小车 → 语音回报

不想用唤醒词时可手动触发：
    echo x > /tmp/voice_trigger
```

**唤醒词**：
- 中文：`小陈同志` / `小陈` / `陈同志`（容错三个）
- 英文：**`Hello, openvela`**（2026-09-19 起；原为 `hi openvela`。`en_hit_rate.py` 里专门实测过命中率）

> 用户反馈「喊 hi openvela 它回复网络不通」—— 这正是这条管线的行为：
> 唤醒成功、提示音「请讲」正常、录音正常，但下一步要调云端 ASR，而网络不通。
> 日志原文：
> ```
> [14:47:17] 🎤 听到唤醒词「hi openvela」（识别到：hi open vela）
> [1] 触发 -> 提示 -> 开始录音
>   唤醒提示：请讲
> [2] 录到 2.12 秒语音 -> /tmp/vb_utt.wav
> [3] 云端预检未通过：代理 192.168.1.100:7890 连不上
> ```

### 管线文档里记的两个坑（我都独立踩到过）

1. **残留的 `arecord` 会永久占住麦克风。**
   `arecord` 收到 SIGTERM 属「优雅退出」，若 stdout 管道已满且无人读，
   它会永远卡在 `write()` 上 —— 杀不掉、麦克风被独占，之后谁录音都报
   `Device or resource busy`。管线现在走 `stop_recorder()`：先关读端 →
   SIGTERM → SIGKILL 兜底。
   → 我的 `speech-bridge.py` 也加了同样的清理逻辑。

2. **写 FIFO 会失败**（助手处理一轮时读端是关的），已改成「挂单」机制。

## 三、⚠️ 我犯过的错误（记录以免重犯）

### 错误 1：把「抢不到设备」当成「硬件坏了」

我最初用 `parecord`/`arecord` 录音得到 0 帧或全 0，就下了
「麦克风采不到声音，硬件问题」的结论。**实际原因**：

- 管线的 `wakeword.py` 用 `arecord` 常驻占用麦克风，我抢不到；
- 我用错了参数（`-c 1 -r 16000`），而厂商样本 `S3Recording.wav` 是
  **4 声道 48000Hz**（对应 adau7118 的 PDM0-3 四路数字麦克风）；
- `parecord` 走 PulseAudio 会卡住不退，进一步独占设备。

**正确做法**：先 `pkill -9 -f arecord`，再用 `-D default` 录音。
改用之后立刻录到真实声音（峰值 2891~16886）。

### 错误 2：以为要用 CSS/自建服务解决一切

我自建了 `speech-bridge.py`，但设备上早已有成熟管线
（含唤醒词、容错、防独占、FIFO 触发、TTS 回报）。
**应该先摸清现有资产再动手。**

### 错误 3：验证方法本身不可靠（见另一文档）

「截图里没光标」「差分法」都被证明是假通过。语音这边也类似：
单看「有没有产出文件」不足以判断，必须看**幅度**与**识别文本**。

## 四、当前实现（speech-bridge.py）

自建服务仍然保留，作为**不依赖云端**的一条独立通路：

```
POST /api/beep    播放提示音
POST /api/record  录音 + vosk 离线识别
GET  /api/health  能力探测
```

关键实现要点：

- **播放必须走 aplay 直连硬件**（`plughw:0,1`）。
  PulseAudio 在本设备上只有 `auto_null`（Dummy Output）一个 sink，
  `paplay` 会返回成功但声音进虚空 —— 典型的「假成功」。
- **录音必须直连 ALSA**，并在录音前 `pkill -9 arecord` 清残留。
- **识别需自行抽单声道**：vosk 只接受 16bit 单声道。

实测返回（如实反映现状）：

```json
{"ok": true, "text": "", "silent": false,
 "frames": 48000, "peak": 2978, "avg": 1108,
 "reason": "未识别到有效语音"}
```

## 五、要真正用起来，还差什么

### 1. 网络（决定云端链路能否工作）

云端 ASR（dashscope）与意图解析（DeepSeek）都需要外网。现状：

```
代理 192.168.1.100:7890   ✗ 连不上
直连 dashscope/deepseek   ✗ 不通
内网 192.168.1.1          ✓ 通
```

若能让 PC 上的代理服务对板子可用（改 `/etc/x3m-proxy.env` 指向可用代理），
现有管线的 `--cloud-first` 就能跑通 —— **这是投入最小、收益最大的改动**。

### 2. 麦克风拾音电平（决定离线识别能否工作）

现场录音平均电平约 1104，接近本底噪声。可尝试：

- 说话时靠近 S3 麦克风（10~20cm）
- 确认 S3 子板安装到位、没有被遮挡
- 检查 `amixer -c 0` 是否有可调的采集增益
  （当前只有 `PDM0~PDM3` 开关与 `CS4344 Control` 音量，**没有采集增益控件**）

> 注意：`CS4344 Control` 是**播放**音量（已 100%），不是麦克风增益。
