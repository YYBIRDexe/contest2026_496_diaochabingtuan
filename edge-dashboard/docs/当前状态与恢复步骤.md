云端提示词 `agent_slow.py` 的"多车清单"同样没有。于是这句话落进"没说车号"的分支。

**修法**：补丁 `_patch_overall_keyword.py`（已部署、幂等、可 `--revert`），

### 新修的 bug：`--car $CAR_IP` 展开为空 → 四台车一台都不动

**现象**：从 PC 经工具桥发「四车前进 0.2 米」，返回 `ok:false` 语义的
`ros_car.py: error: argument --car: expected one argument`，**退出码 2，车没动**。

**根因**：`vcmd_actions.json` 的命令模板写的是
`ros_car.py --car $CAR_IP --robots "$ROBOTS" ...`。
语音路径能动，是因为 `voice_button.py` 在环境里设了 `CAR_IP`；
**命令行 / SSH / MCP 工具桥这条路径没人设**，shell 把 `$CAR_IP` 展开成空字符串，
argparse 在 `--robots` 生效之前就报错退出。

这也解释了为什么"昨天语音能动、今天工具调用不动"——**不是网络问题，是环境变量缺口**。

**修法**（补丁 `03-大赛送审材料\演示视频\tools\_patch_vcmd_car_ip.py`，已部署、幂等、可 `--revert`）：
`run_env` 构造后若 `CAR_IP` 为空，用 `robots.json` 的 1 号车兜底。
因为 `ros_car.py` 里 **`--robots` 优先于 `--car`**（实测第 551~556 行），
目标车仍由 `ROBOTS` 决定 —— 这个兜底只为了让 argparse 拿到一个非空值。

**回归**（四个场景都 dry-run 验过）：语音路径设了 `CAR_IP` 时行为不变；
`ROBOTS` 仍压过兜底；PC 路径 `--robots all` → `1,2,3,4`、`--robots 2` → 单台。
`vcmd.py --selftest` 9/9、`nlp_parse.py --selftest` 27/27 全绿。

> ⚠️ **回滚注意**：本补丁的备份 `vcmd.py.bak-before-carip-*` 里**没有** `--robots` 补丁
> （那个补丁更早打的）。`--revert` 已改成优先"按补丁段反向移除"，
> 不要图省事整文件还原，否则会把 `--robots` 一起弄丢。

### 现象 1：说「四辆小车都连上了吗」，没有语音回复、也没有文字回复

**先摆事实**（设备 `/tmp/voice_text.jsonl` 里那一轮真的存在）：

```json
{"ts":"2026-09-17 17:31:31","text":"四辆小车都连上了吗？","source":"agent",
 "steps":[{"intent":"car_check","params":{}}],
 "step_results":[{"intent":"car_check","cmd_text":"四辆小车都连上了吗？",
                  "rc":0,"commands":["python3 .../check_cars.py"],"executed":true}],
 "plan_ok":true}
```

也就是说：**识别、意图、执行全都成功了**，`check_cars.py` 也返回了 0。
问题出在「结果怎么回到用户眼前」这一段，一共三个独立缺陷：

| # | 缺陷 | 证据 | 修法 |
| - | --- | --- | --- |
| A | **僵尸 `aplay` 被当成「正在放音」** | `ps` 里长期挂着 `79196 [aplay] <defunct>`；桥的 `_playback_running()` 用 `pgrep -f aplay` 判断，僵尸也匹配 → `_wait_playback_done()` 每轮白等满 40 秒才超时 | `_playback_running()` 逐个查 `ps -o stat=`，`Z` 状态不算放音；等待窗口 6+40 秒收到 3+20 秒。受控实验见 `tools/vnc/scripts/verify-zombie.sh` |
| B | **唤醒引擎其实已经死了** | 进程表里 `78067 [python3] <defunct>`；`voice-assistant.service` 处于 `failed` → 桥 kill 掉唤醒引擎后没人再拉起 → 喊「hi openvela」永远没反应 | 桥的 `_resume_wakeword()` 改成**先手动拉起唤醒引擎**（载入 `/etc/x3m-proxy.env` + `选代理.sh` 后再起 `wakeword.py`），起不来才退回「重启服务」；另外把服务拉回 `active`（现在助手/唤醒/arecord 三个进程齐） |
| C | **设备上跑的是旧版界面** | 设备 `~/velaguard/preview/index.html` 里 `chatPinned`=0、`voice/start`=0（本地新版分别是 4 和 1） | 重新构建 + 部署（见下） |

**顺带修掉一个会让「设备说了但界面不知道」的坑**：
`@@SPEAK@@` 播报的那句话（如「小车都联系不上」）以前**不写进记录**，

### 现象 2：左侧聊天界面弹出新文字后依旧不自动下滑

**根因是两个，都不是「滚动代码写错了」这么简单：**

1. **设备上的产物是旧的**。源码里 `pushMessage()` 会调 `scrollChatToBottom()`，
   设备上那一版根本没有这个函数（`grep scrollChatToBottom` 命中 0），
   自动下滑全靠框架层兜着 —— 而框架层当时有第 2 条这个 bug。
2. **框架层「首次撑出滚动条」那一次不贴底**（真 bug）：
   `snapshotScroll()` 只快照**已经能滚**的容器，于是「内容刚刚够长」那一次
   快照是空的 → `restoreScroll()` 直接 `return` → 新消息进来就停在顶部。
   用户的原话正是「弹出新的文字后依旧没有自动下滑」。

修法：框架层把带 `data-auto-bottom` 的容器**无论当前有没有溢出都纳入快照**；
界面侧同时补齐 `scrollChatToBottom()` + `chatPinned`（往上翻历史时不打扰）。
回归测试新增两条（`tools/test-chat-scroll.js`，现 24 项）：

```
✓ 首次撑出滚动条时自动贴底（框架层还原）
✓ 设备侧新记录会自动出现在会话区（1 -> 3 条气泡）
✓ 轮询进来的消息内容是设备的播报（助手小车都联系不上）
✓ 轮询进来后会自动贴底
```

> **测试本身也修了一个隐蔽的坏味道**：以前用 `getData().messages = [...]`
> 改数据来断言滚动 —— 那是**原始对象、绕过 Proxy**，数据变了但 DOM 不重绘，
> 于是「不会跳回顶部」这类断言**永远成立**（空断言）。
> 现在统一走新增的 `window.__velaguard.patch({...})`，
> 并加了「新消息确实渲染了」这条前置断言。写测试时务必用 patch。

## 零之一、语音与文字的同步（2026-09-19 05:50，用户报"文字晚 10 秒"）

**现象**：回复时先听到语音，约 10 秒后文字才出现。用户要求：①降低延迟 ②语音文字同步。

**先量，再改**。给一轮语音的关键节点打上时间戳后，真相是：

```
19.155 vcmd 执行完 → 19.171 播报开始（语音出声）
19.192 记录落盘（+0.02s）→ 19.291 桥的接口已能查到（+0.12s）
```

**记录一直紧跟语音** —— 所以 10 秒不是"生成慢"，而是"界面查不到"：

| 根因 | 说明 | 修法 |
| --- | --- | --- |
| **桥是单线程的** | 界面按「结束」时发的 `/api/voice/stop` 会在服务端阻塞若干秒，后面每 2 秒一次的轮询全被**排队**，文字只能等那个请求返回 | 换成 `ThreadingHTTPServer` |
| stop 请求还白等播报 | `_wait_playback_done()` 是早期为了"别把正在播的 aplay 杀掉"加的，而现在恢复唤醒引擎早就不杀服务了 | stop 路径 `wait_playback=False`；`/api/voice/talk` 保留旧行为 |
| 恢复唤醒引擎占着请求 | 起进程 + 载模型要 3~5 秒 | 挪到后台线程（`_resume_wakeword_async`） |
| 轮询间隔 2 秒 | 间隔直接决定"文字比语音晚多少" | 改成 **1 秒**；stop 的 wait 8→2 秒 |

**实测（真机、按钮流程、喇叭代替人说话）**：

```
01:48:54.463  答案语音开始（aplay 557357aa…）
01:48:54.958  桥的接口已能查到这条记录      ← 语音开始后 0.48 秒
01:48:56.821  答案语音结束
stop 请求耗时 3653 ms（原来 17.2 秒）
```

并发实测（一个慢请求占着桥时轮询的往返时间）：**43~51 ms**（修复前会被串行卡到秒级）。
结论：文字现在**落后语音 ≤1.5 秒**（记录 0.5s + 轮询 1s），原来约 10 秒。

**剩下的延迟构成**（同一条语音实测，从"按结束"到"语音出声"约 3.5 秒）：

| 环节 | 实测 | 能不能再省 |
| --- | --- | --- |
| 录音收尾 + 转 16k + 联网预检 | 0.4 秒 | 预检偶尔要 4 秒（可加缓存，未做） |
| 云端 ASR | 1.0~12 秒 | **省不了**（这是大头上限） |
| 云端模型判意图（`--cloud-first`） | 0.94 秒 | 可以省：见下面「可选优化」 |
| vcmd 执行（查车/读电量） | 0.6 秒 | 车端探测时间，省不了 |
| TTS 合成 | 缓存命中≈0；未命中 1~3 秒 | 可预合成常用短语 |

> **可选优化（没做，等用户拍板）**：把设备上的 `--cloud-first` 去掉，改成
> **本地规则优先**（认不出再交云端）。实测同一条语音可省 **约 0.94 秒**，
> 且 13 个意图的本地规则本来就能覆盖（`nlp_parse --selftest` 24/24、`run_tests` 71/71）。
> 代价：本地规则"认错但认得出"的句子会直接执行，不再经过云端复核 ——

### 现象

### 根因（两个独立问题）

**问题 A：PC 的系统代理指向死端口**

```
注册表 ProxyServer = http://127.0.0.1:65532    ← 没有任何程序在监听

修法：关掉系统代理（`ProxyEnable=0`）。

> 这是代理工具异常退出时没清干净留下的残留，很常见。
> 判断方法：`Get-NetTCPConnection -LocalPort <代理端口> -State Listen` 看有没有人在听。

**问题 B：笔记本重启后，SSH 反向隧道没起**

设备没有公网出口，唯一的路是：

```
设备程序 → http_proxy=127.0.0.1:7890（设备本机）
         → SSH 反向隧道（笔记本主动发起，绕过 Windows 防火墙）
         → 笔记本 127.0.0.1:7890（local_proxy.py）
         → 校园网 → DashScope / DeepSeek
```

笔记本一重启，`local_proxy.py` 和隧道进程都没了 → 设备断网 →
云端 ASR / TTS / 意图模型全失败 → 只回一句「网络不通」。

这**正是** `语音能说什么-速查表.md` 第 4 节第 6 条写的情况，也是

## 三点五、「说话」按钮的交互与实现（2026-09-19）

| 结果 | 识别到的话以「你」的气泡显示；设备的语音回报以「助手」气泡显示 |

### 它走的是设备自带的完整链路

```

会被「麦克风被占用」丢弃 —— 这是 `voice_pipeline` 文档明确记录的行为。

## 四点五、会话记录滚动的修复（2026-09-19）

### 现象与根因

用户反馈：**聊天记录自己跳回顶部**，而且右侧滑动体验差。

**根因**：预览页的 `doRender()` 是**整棵 DOM 重建**：

```js
rootEl.textContent = ''      // ← 滚动位置在这里归零
rootEl.appendChild(frag)
```

每次 `pushMessage()` 改数据 → 触发重建 → 滚动位置丢失 → 表现就是「跳回顶部」。

### 修法（框架层，`tools/build-preview.js`）

1. 重建前 `snapshotScroll()` 记录所有可滚动元素的 `scrollTop` 与是否贴底
2. 重建后 `restoreScroll()` 按出现顺序还原
3. 带 `data-auto-bottom` 属性的容器（如会话区 `.chat`）：
   - 重建前若贴着底部 → 继续贴底（新消息自然跟随下滚）
   - 重建前若已上翻 → **如实保留位置**，不会被拽回底部

### 回归测试

`tools/test-chat-scroll.js`（已纳入 `npm test`），9 项全通过：

```
✓ 会话区带 data-auto-bottom 标记
✓ 上翻时新增消息不会跳回顶部（120 -> 120）    ← 核心修复
✓ 在底部时新消息自动跟随下滚
✓ 会话区高度 660px / 宽度满屏
```

> **写测试时踩的坑**：`window.__velaguard` 是宿主桩件，组件数据要用
> `getData()` 拿；而且直接把整个数组赋给 proxy（`d.messages = [...]`）
> **数据会变但 DOM 不重绘**。用页面自己的 `pushMessage` 循环追加才对 ——
> 那也正是真实加消息的代码路径。

### 坑 1：`Start-Process` 把 stdout/stderr 重定向到**同一个文件**会静默失败

```
方式 A：同一日志文件   → ✗ 进程数=0，端口没监听，日志里也没有任何报错
方式 B：分开的日志文件 → ✓ 成功
方式 C：不重定向       → ✓ 成功
```

两个重定向抢同一个文件句柄，子进程根本没起来。**必须用两个文件**
（现在用 `proxy.out.log` / `proxy.err.log`）。

### 坑 2：`pythonw.exe` + 重定向也会立刻退出

`pythonw` 没有控制台流，配 `-RedirectStandardOutput` 时会在绑定端口前就退出。
改用 **`python.exe` + `-WindowStyle Hidden`** —— 同样无窗口，但能正常绑定。

### 坑 3：`-WorkingDirectory` 传中文路径会报 DirectoryNotFoundException

`Start-Process -WorkingDirectory "F:\xiaomiaiot\runtime\tunnel"` 失败，
但同一路径 `Test-Path` 是 True。**不传 `-WorkingDirectory`，
只用绝对脚本路径**即可。

### 坑 4：隧道断掉后，设备侧 sshd 会把端口留着且无属主

表现：反向隧道报 `remote port forwarding failed for listen port 7890`，
但设备上 `ss -ltnp` 看不到占用的进程（没有会话进程挂在这个 socket 上），
因此**杀不掉**。

处理：`autostart.ps1` 会先尝试清孤儿会话；清不掉就**自动换下一个端口**
（7890 → 7891 → 7892）。设备侧 `选代理.sh` 的 `TUNNEL_PORTS` 探测同一组端口，
两边要一起改。
