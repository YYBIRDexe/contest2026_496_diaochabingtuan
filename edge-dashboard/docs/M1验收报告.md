## 三、踩过的坑（供后续维护参考）

1. **Firefox 无头渲染在这台设备上不可用**
   `firefox --headless --screenshot` 报 `RenderCompositorSWGL failed mapping default
   framebuffer, no dt` 并挂起。**必须走真实 X 会话 + 外部截图工具。**

2. **`--profile` 指向不存在的目录会失败**
   弹 "Profile Missing" 后退出。要么先建目录，要么干脆不带 `--profile`。

3. **`PIL` 读不了 XWD**
   正确链路是 `xwd -root` → `ffmpeg -i x.xwd x.png`。抓一屏约 8.3MB，转 PNG 后约 140KB。

4. **内存是硬约束**
   设备上原有 Firefox 占 385MB（在用 `/run/x3m-campus/status.html`）。释放后可用内存
   从 641MB 升到 1069MB，看板 Firefox 稳定占用约 260MB。

5. **SSH 与图形会话是分开的**
   SSH 里 `DISPLAY` 为空、`xrandr` 不可用；查询屏幕需显式
   `DISPLAY=:0 XAUTHORITY=$HOME/.Xauthority`。

6. **`scp` 不解析 `~` 与 `$HOME`**，必须用绝对路径（如 `/home/sunrise/velaguard`）。

7. **VNC 输入注入走不通**（本次走过的弯路，已放弃）
   RealVNC Viewer 忽略 `PostMessage`（走底层输入）；`SendInput` 又被前台锁挡住
   （`SetForegroundWindow` 返回 False）。**结论：不要试图用 VNC 驱动远端操作，
   有 SSH 就用 SSH。**

## 四、分辨率：设计基准已确认为 1280×800

用户确认目标分辨率为 **1280×800**。已按此做了两件事：

### 1. 修正了一个会误导验收的问题（已完成）

交付的预览页原先在视口大于 1280×800 时会把界面**放大填充**，
因此在 M1 的 1920×1080 屏上看到的是放大 1.5 倍的版本，**并非 1280×800 下的真实观感**。

现已改为**最大 1:1**：

```js
const scale = fit ? Math.min(availW / DESIGN.width, availH / DESIGN.height, 1) : 1
```

- 视口 **小于** 1280×800 → 等比缩小，内容完整可见
- 视口 **大于** 1280×800 → 保持 1:1 **不放大**，居中显示

**效果**：无论在哪台机器上打开，看到的都等同于 1280×800 下的实际效果。
最新真机截图 `preview/m1/m1-kiosk.png` 即为此模式——界面本体严格 1280×800。

### 2. M1 的 X 当前固定在 1920×1080（**xrandr 改不动**）

实测：

```
Screen 0: minimum 1920 x 1080, current 1920 x 1080, maximum 1920 x 1080
default connected 1920x1080+0+0 0mm x 0mm
   1920x1080     60.00*
```

**只有一个模式**，min/max 都被卡在 1920×1080，`xrandr --addmode` 无可用模式可加。
查到的原因：

- 内核引导参数含 `video=hobot:x3sdb-hdmi` → **显示模式在内核引导层确定**
- `/sys/class/drm/` 下没有标准 connector 节点（`card*/card*-*/`），无法走 DRM 改模式
- 没有 `/etc/X11/xorg.conf`，也没有启动脚本里的 `xrandr`

> 若要硬改，需调整内核 `video=` 引导参数或显示 DTS，**有把显示搞黑的风险**，
> 不建议在没有备份的情况下动。见下方方案。

### 结论：说明书标注不可信，实测屏为 1920×1080

用户最终选择**方案 B：按屏幕实际比例重新设计**（而不是把输出改成 1280×800）。

| 方案 | 做法 | 结果 |
| --- | --- | --- |
| A. 输出侧改 1280×800 | 需改内核引导参数 | 已实测不可行（xrandr 无可用模式），且屏本身是 16:9 |
| **B. 按 1920×1080 重新设计（已采用）** | 改设计基准并重排布局 | **界面 1:1 铺满整屏，四边零黑边** |

### 方案 B 落地结果（已完成）

改动内容：

1. `src/manifest.json`：`designWidth` 1280 → **1920**，新增 `designHeight: 1080`
2. `tools/build-preview.js`：设计高度改为从 manifest 读取；**缩放改为铺满屏幕**
   （`?scale=1` 可切回 1:1 评审模式）；修正外框尺寸自适应，避免小窗口下裁掉底部内容
3. `src/pages/Home/index.ux`：磁贴改 3 列 × 600（1920 宽整除）排成 3 + 2；
   新增**区域状态条**填充宽屏纵向空间；字号整体提升；压缩纵向尺寸避免与快捷坞重叠
4. `src/pages/Dispatch|Zones|VoiceAssistant`：侧栏 / 卡片 / 气泡宽度按 1920 放大

**真机验证（`preview/m1/m1-kiosk.png`）**：

| 检查项 | 结果 |
| --- | --- |
| 黑边（四边） | **0 / 0 / 0 / 0 px** |
| 内容区 | **1920×1080**，比例 1.7778（与屏幕完全一致） |
| 判据 | `tools/vnc/check-fill.ps1` → `VERDICT: FILLED` |

## 七、开机自启验证（真机重启实测）

### 验证方法

不能靠读 `.desktop` 文件证明自启动有效，必须实际重启观察：

1. 记录重启前状态（uptime、PID）
2. 执行重启，**确认连接真的断开、uptime 归零**
3. 等 SSH 恢复，再等桌面与自启完成
4. 逐项检查：自动登录、看板进程、渲染判据、校园网页是否被误启

> ⚠️ **踩过的坑**：第一版写成
> `sudo -n reboot || systemctl reboot`，被 `||` 短路，
> 重启根本没执行，而后续检查全部通过，于是**误判为验证成功**——
> 最后是 `uptime` 仍显示「1 小时 9 分」才暴露出来。
> **判据必须是「uptime 归零 + 连接断开」，不能只看命令返回值。**

### 实测结果

| 检查项 | 结果 |
| --- | --- |
| 系统重启 | ✅ `up 0 minutes`、`已开机 31s` |
| **自动登录** | ✅ `桌面会话=1`、`登录界面=0` |
| 数据服务自启 | ✅ `serve.js`（重启后新 PID） |
| 看板自启 | ✅ `firefox --kiosk http://127.0.0.1:8123/#kiosk` |
| **看板渲染** | ✅ 暗像素 96.0% |
| 鼠标光标 | ✅ 已隐藏（递归窗口树 + 常驻跟进，差分法验证 DIFF=0） |
| 校园网状态页 | ✅ 未启动 |

**结论：开机 → 自动登录桌面 → 自动全屏进入触控操作页面，全程无需人工干预。**

证据截图：`preview/m1/boot-verified.png`

### 重启命令（供后续使用）

`sudo` 需要密码（NOPASSWD 只放行两个代理脚本），但本机会话是
`Type=x11 / Active=yes / Remote=no`（本地活动会话），以下方式可用：

```bash
systemctl reboot
# 或
xfce4-session-logout --reboot --fast
```

若提示 `Interactive authentication required`，需在设备上手动重启。

## 八、语音助手验证

### 降级逻辑正确

该页依赖 openvela 的 `@system.velaclaw`（端侧 AI），本设备没有，
实测**自动降级为本地指令模式**：

- 右上角徽标显示「本地指令模式」
- 底部提示「外部 AI 不可用（code 404），已切换为本地指令」

### 页面完整可用

`#kiosk,voice` 路由直达后截图确认：标题栏、会话气泡、5 条常用指令
（开始本轮巡检 / 现在哪些区域没查完 / 展项区为什么阻塞 / 取消全部未完成任务 /
生成巡检报告）、底部「按住说话 / 发送」齐全。暗像素 95.7%。

### 修掉一个静默 bug

`start.sh --page voice` 会生成 hash `#kiosk,voice`，但预览页的
`initialPage()` 原先拿整串 `"kiosk,voice"` 当页面名匹配，**匹配不到就静默
回退首页**，导致 `--page` 参数形同虚设。已改为按逗号分词逐个匹配，
并补了 8 项回归测试锁住该行为。

### 交互验证的局限（如实说明）

`xdotool` 的合成输入在本设备上**不被 Firefox 接收**：
指针位置能改（X 层可见）、窗口在前台且订阅了 `ButtonPress`/`PointerMotion`、
无 grab 重定向，但页面**连 hover 都没有**（两次截图 md5 完全相同）。

因此**页面内的逐步点击交互无法自动化验证**，需要人工在触摸屏上确认手感。
本页的渲染、降级、数据链路均已验证；点击后的具体应答逻辑已由
`tools/test.js` 在无头浏览器中覆盖。
